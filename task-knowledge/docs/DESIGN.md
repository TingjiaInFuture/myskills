# 设计记录：将大索引留在机器上，把小结果交给模型

## 决策

对于本次给定资料，选择 **文件事实源 + SQLite FTS5 倒排索引 + 带预算的 CLI**。原包实际只有 SKILL.md 和两个模板，没有业务数据库、原有检索程序或真实存档数据，因此实现从兼容原 brief 格式出发，而不是迁移一个并不存在的旧系统。

不用向量检索来解决最初的关键词需求；不设 Web API、MCP server、ORM、队列、容器或后台 watcher。搜索能力的执行边界是一条命令，AI 的协议边界是一份 JSON。唯一运行时文件 kb.py 可直接复制运行。

```text
人工/AI 编辑 brief ── sync ID ──→ docs + docs_fts（一个事务）
                                       ↑
关键词 ── 规范化/安全编译 ──→ MATCH + rank + LIMIT
                                       ↓
                          top-K 元数据 + 相关行
                                       ↓
                             UTF-8 JSON 字节预算
                                       ↓
                              AI 复核、必要时 get
```

## 为什么 SQLite 是索引，不是唯一存储

保留 brief 的人工可读性、Git diff 和已有工作流，数据库可以随时从它重建。将唯一资料迁进数据库会额外需要编辑器、导出、附件管理和资料迁移，不符合当前“最简”目标。

代价是必须定义同步协议；本实现不隐藏这一代价。文件写入和数据库提交不是同一事务。修改完成后主动 `sync ID`，失败则报告索引待更新；外部批量改动后手动全库增量扫描。search 不做隐形同步，避免每次查询 O(N) 的目录扫描。

## 检索粒度与质量边界

一条 brief 对应一条文档。原 Skill 已要求 brief 很短，因此这里不再做 chunking；给短摘要切块再聚合只会增加 ID、排序与一致性复杂度。长 experience 默认不入库，减少无关命令、路径、过程记录污染召回。

标题（含目录名）/关键词/摘要/经验要点是四个检索字段，起始权重 8/6/3/1。SQLite 自己完成全匹配集上的 BM25 排序，没有先拉100条再在 Python 中猜“全局Top-K”的近似步骤。相同分数之间不保证稳定顺序；分数不是跨库可比的相关性概率。

只有词法能力，不具备自然语言问句理解、繁简转换、同义词/跨语言向量召回或拼写纠错。已存在的 AI 从任务中抽关键词，在 brief 中维护别名，能避免为这个小工具再增加模型和词典依赖。连续中文词要求连续出现；英文以完整归一词为单位。any 模式适合初筛，all 模式提高约束，但会牺牲召回。

本次未提供真实检索评测集，因此不能证明这组字段权重“质量最佳”。示例与单元测试只证明定义的词法行为；合成基准只衡量性能。如果以后真实评测发现词面无交集造成大量漏召回，再增加向量召回并做质量对比，不提前建设。

## 中文 token 设计

不直接依赖 unicode61 对无空格中文做有意义的词切分；不单独用 trigram，因为不足三个 Unicode 字符的 FTS 查询不能命中 trigram 索引。采用预分词后的 `ascii` tokenizer，保留所有非 ASCII 字符，其有限的大小写处理由 Python 的统一规范化补足。[FTS5 tokenizer 官方文档](https://www.sqlite.org/fts5.html#tokenizers)

`数据库` 变为 `b数据 b据库 x u数 u据 u库 x`。连续中文片段先写双字序列，再写单字序列，中间/末尾各插保留边界 x。查询多字词编译为一个带引号的双字 token phrase，而不是松散 OR；查询单字使用 u 通道。这样可以匹配真实连续子串，又不会把两个位置分开的重叠双字错拼成命中。

非汉字词添加 w 前缀，因此资料中的字母 x 不会误命中内部边界。词法器只产归一后的字母数字词，生成 MATCH 时统一引用；SQL 参数另外绑定。预处理 token 不交给模型，仅用原文产生标题、摘要与相关行。

用单字+双字意味着更大的索引，换来短中文无需全表 LIKE 兜底。external-content 避免 FTS 再保存一份字段内容，但 docs 中仍有原 brief 与预分词字段；本方案不宣称比 Markdown 更省磁盘。具体放大率以随包基准为准。

## 同步与一致性

数据库身份使用 application_id/user_version；同时记录根目录，拒绝将属于别的库的索引误作本库缓存。内容表用稳定 rowid，slug 唯一。新增/删除/全文字段更新用触发器同步 FTS，避免检索与元数据各自成功一半。[SQLite external-content 风险与触发器](https://www.sqlite.org/fts5.html#external_content_table_pitfalls)

定向 sync 对每个目标做路径检查与 stat；mtime/size 未变就跳过读文件，疑似变化则 SHA-256 比对。单纯触碰时间戳时只更新 stat 元数据，不触发全文重写。无 ID 的 sync 才枚举一层目录，并在枚举成功之后移除消失的记录。任何失败均回滚这一批数据库变更；没有“读取失败等于已删除”的误判。

sync --full 强制哈希，但不是修复 FTS 的命令；FTS 与内容不一致时用 doctor 检测、rebuild 重建。rebuild 的 DDL、重新扫描与提交在同一个原库事务中，不对正在使用的 DB 执行危险的文件替换。数据库本体不可读时换一个新缓存文件，不承诺通过普通SQL修复磁盘坏页。

WAL 支持同机读写并行快照，写者仍串行。事务只保证数据库内部一致，目录遍历不是文件系统快照；并发目录编辑可能需要再 sync 一次。因此也不能把“最近同步时间”当作资料实时一致性的证明。[SQLite WAL](https://www.sqlite.org/wal.html)

## 复杂度：避免不真实的 O(log N) 承诺

令 N 为存档数，M 为实际变化/定向同步的存档数，P 为查询命中的倒排项数量，K 为输出条数。

定向同步主要与 M 个文件的读取/分词和索引更新有关；全库增量 sync 仍有 O(N) 的目录/stat/元数据工作。search 不遍历 N 个源文件，不对全体 brief 做 Python 评分，但它的数据库开销依赖词频及匹配集 P，不能简单声称 O(log N) 或 O(K)。极常见词可能匹配全库并需要计算大量分数，LIMIT 不会让这些计算自动消失。

Top-K 的序列化与源文本解析只作用于取回的行，K 被限制为1–50，每份源文件有大小上限。输出由 JSON 字节预算独立约束，不随 N 线性增长；不表示精确模型 token 总数固定。

## 预算设计

默认6000字节，包含UTF-8、多字节中文、JSON转义、元数据和换行。超预算先缩短 snippet，再 summary，再丢弃最低排名记录。路径保持完整；输出始终合法JSON，不按字节硬截原串。预算太小可能没有一条完整元数据能容纳，返回空列表但 budget_limited=true，用来区别无命中。

get 只读用户选定的某一个 brief 或 experience。该源文件比缓存更新也不触发隐形全库同步。内容不足以放入预算时通过二分确定能完整序列化的前缀并标 truncated=true。

## 明确不提供

多用户权限、分布式数据库、网络共享 WAL、附件/PDF/OCR 索引、任意SQL/FTS接口、语义检索模型、全局自动监控、源文件自动合并/删除、密钥管理、加密与安全擦除都不是这次实现的功能。安全防护针对本地个人使用，不构成抵御恶意同账户并发操作的文件系统沙箱。

## 可扩展而不先过度设计

未来确实有需要时，可以在现有Python进程中直接调用 KnowledgeBase，避免解释器冷启动；对真实查询建立可重复的相关性样本，再考虑调权重或引入第二条召回路径。当前交付已经包含直接Python接口，无须为了毫秒级SQL建立长期运行的额外服务。
