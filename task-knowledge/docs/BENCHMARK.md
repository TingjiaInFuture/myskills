# 性能实测与限制

## 测量条件

执行日期：2026-09-08。原始记录：[benchmark-10000.json](benchmark-10000.json)。

环境：Linux-6.18.35-x86_64-with-glibc2.41；Python 3.13.5；SQLite 3.46.1；容器报告 5 个逻辑 CPU。存储为临时目录，未清除操作系统缓存。这些数据是本次环境的实测，不是用户机器的承诺或通用 SLA。

```bash
python -S scripts/benchmark.py --docs 10000 --runs 30 --cli-runs 5 --output docs/benchmark-10000.json
```

生成10,000条中文/英文合成 brief，分10个主题，各1,000条，每条包含一个唯一词及全库共有词。它们高度规律，**不能代表真实知识库的相关性或准确率**。本轮只证明这种负载下的性能，没有百万规模、冷盘查询或真实用户语义召回结论。

## 查询耗时

下表单位均为毫秒。SQL 与 API 各30次，CLI 各5次；CLI 的样本数较少，p95 在此就是该组最大观测值，不应视为稳定的尾延迟估计。

| 查询 | 命中文档 | SQL中位数 | API中位数 | 普通CLI中位数 | `-S` CLI中位数 | `-S` CLI p95 |
|---|---:|---:|---:|---:|---:|---:|
| 唯一词 `needle9999` | 1 | 0.063 | 0.790 | 826.650 | 71.288 | 141.498 |
| 主题词 `sqlite 中文检索` | 1,000 | 1.646 | 3.075 | 897.426 | 85.174 | 96.785 |
| 全库常见词 `shared` | 10,000 | 11.256 | 12.517 | 882.158 | 82.482 | 112.307 |

SQL 微基准复用已打开连接、预热查询，并且只取 slug/rank；它不含源 brief 快照取回、片段组装或 JSON 输出。API 测量包含打开/关闭连接、取回 Top-K、生成片段和预算检查。CLI 每次启动新解释器，包含完整命令调用与序列化输出，没有把 SQL 的1–2毫秒冒充端到端耗时。

普通 Python 在此容器中的 site 初始化开销明显较高。无第三方依赖的程序可用 `-S` 跳过它，但收益并不保证在其他系统相同；`-S` 不提供安全隔离。[Python 官方 -S 说明](https://docs.python.org/3/using/cmdline.html#cmdoption-S)

查询计划采用 FTS 虚表 MATCH 游标，再以 rowid 查文档表，没有 Python 全库评分。计划文本中的 `SCAN docs_fts VIRTUAL TABLE INDEX 32:M4` 是虚表查询计划，不意味着在文件系统读取每份 brief。常见词仍可能需处理全库匹配项；结果 LIMIT 5 不等于只计算5条。

## 写入与空间

| 项目 | 实测 |
|---|---:|
| 初次构建10,000条 | 6.5841 秒 |
| 无变化全库增量对账 | 0.7570 秒 |
| 定向同步一条修改 | 3.300 毫秒 |
| 源 brief 内容总字节 | 5,693,780 |
| SQLite 主文件字节 | 41,439,232 |
| SQLite 主文件大小 | 39.52 MiB |

无变化对账读取0份 brief 正文，但仍枚举一层目录并 stat，所以它不在每次 search 的默认路径上。定向同步不枚举其他存档。同步计数器原始值均保留在 JSON 中。

本次数据库约为源 brief 字节的 7.28 倍：原文快照、归一化字段、单双字 token 和倒排数据都会占空间。该方案以本地磁盘换取词法检索和小上下文，不宣称节约磁盘。主文件大小在写连接关闭后测量；文件系统目录/块开销未计入源文件字节。

## 上下文输入对比

相同合成资料按照旧模板生成的全量索引行共 **1,231,890字节**。
主题查询的 Top-5 完整 JSON 为 **1,919字节**，本次比读取全量索引减少约 **99.84%** 的检索结果输入字节。

这是检索工具输出与全量索引文本之间的对比，**不是精确 token 测量**，不包含系统提示、工具调用包装、用户问题、AI 输出或后续 get。路径长度、摘要内容、K 和预算不同，结果也不同。默认预算6000字节是序列化结果的硬上限，而不是“固定6000 tokens”。
