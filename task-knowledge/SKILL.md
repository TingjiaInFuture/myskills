# 任务经验沉淀复用（task-knowledge）

管理个人任务知识库（KB）：把每次成功任务的可复用经验与最少完整上下文沉淀为**相互独立**的存档，并在后续任务中检索与复用。

## 功能速查

| 功能 | 典型触发 | 核心动作 |
|---|---|---|
| 1 存档 | 任务成功完成，"存档/沉淀本次任务" | 查重 → 新建存档文件夹 + brief.txt → 登记 INDEX |
| 2 检索 | "查之前的经验"、给出一段任务描述 | INDEX 初筛 → 读 brief 复核 → 输出最相关的几个 |
| 3 更新 | 存档时查重命中已有存档 | 增量合并 + 追加更新记录 → 同步 INDEX |
| 4 复用 | "复用经验做 X"、新任务开始 | 检索 → 读 brief（按需深入）→ 应用到当前任务 |

## 配置

- **KB 根目录**（下称 `KB_ROOT`）：默认 `~/knowledge/`（Windows 下即 `C:\Users\<用户名>\knowledge\`）。若用户在会话中指定过其他目录，以用户指定为准。
- 结构：

```
KB_ROOT/
├── INDEX.md              # 索引：每个存档一行摘要（检索入口，随存档/更新必须同步）
└── <凝练标题>/            # 一个任务一个存档文件夹，存档之间相互独立
    ├── brief.txt         # 必需：总览入口，用于快速判断相关性
    ├── experience.md     # 可选：详细经验（命令、配置、踩坑过程、方案对比）
    └── assets/           # 可选：仅当引用对象易失效且必须复制时使用
```

- **参数分流**：带参数调用时按第一个关键词分流——`存档/archive`→功能 1；`检索/搜索/search <prompt>`→功能 2；`更新/update`→功能 3；`复用/reuse <任务描述>`→功能 4。只给一段任务描述、无明确动词时，默认执行**检索**。

## 功能 1：存档（archive）

**触发**：本次任务已成功执行完毕，且满足价值标准（见下）。满足时主动存档并报告；不满足时跳过。

1. **判断价值**（三条都满足才存档）：
   - 任务成功（或失败但已定位出可复用的根因与规避方法，可作"坑"记录）；
   - 以后大概率还会遇到类似任务；
   - 有超出常识的可复用要点（做法/命令/配置/决策/坑）。
   - 仅改错别字、纯问答、纯一次性操作 → 不存档。
2. **查重**：读 `KB_ROOT/INDEX.md`（不存在则视为空库）。若已有存档与本次主题相关（同领域/同问题/同方法）→ **停止新建，转功能 3（更新）**。
3. **命名**：文件夹名 = 本次存档的凝练标题。规范：`主题-要点` 的 kebab-case 英文或简短中文，≤30 字符，不含空格，用词便于日后关键词匹配（如 `powershell-batch-rename`、`git-subtree-拆分仓库`）。
4. **写 `brief.txt`**：按 [assets/brief-template.txt](assets/brief-template.txt) 结构，全文 ≤40 行。要点：
   - 摘要一句话说清"解决什么问题、核心做法"；
   - 关键词写日后检索会用到的词（中英文均可）；
   - **上下文引用只写绝对 path**，每个 path 一行说明，不把文件内容抄进 brief；
   - 经验要点少而精（结论级），展开内容放 `experience.md`。
5. **经验较多时**：把命令细节、完整踩坑过程、备选方案对比写入 `experience.md`，brief 只留结论。
6. **登记**：在 `INDEX.md` 末尾追加一行（格式见 [assets/index-template.md](assets/index-template.md)）。
7. **报告**：告知用户存档路径与标题。

## 功能 2：检索（search）

**触发**：用户给出 prompt/任务描述要找相关经验；或作为功能 4 的前置步骤。

1. 读 `KB_ROOT/INDEX.md`，按标题、摘要、关键词与输入匹配，选出前 3–5 个候选。库为空 → 直接告知无存档。
2. **兜底**：INDEX 缺失或与实际文件夹明显不符时，用 Glob 列出 `KB_ROOT/*/brief.txt`，再用 Grep 按关键词过滤，并顺手按模板重建 INDEX。
3. 读取候选存档的 `brief.txt`（**只读 brief**，不读 experience.md 和引用文件），按相关度排序。
4. **输出**：候选列表（存档文件夹路径 + 一句话说明为何相关 + 命中关键词），并明确推荐最相关的 1–2 个。无相关存档时如实说明，不硬凑。

## 功能 3：更新（update）

**触发**：存档查重时发现已有相关存档；或用户明确要求更新某个存档。

1. 用功能 2 定位目标存档；多个候选相关时选最贴近的，并向用户确认。
2. **增量合并**，不做全文重写：
   - 新经验要点去重后追加；
   - 被本次任务推翻/过时的条目改写或标注"已过时"；
   - 补充缺失的上下文 path；已失效的 path 移除或标注。
3. 在 `brief.txt` 的"更新记录"追加一行：`YYYY-MM-DD <一句话变更摘要>`；摘要/关键词如有更准确表述一并刷新。
4. **判断是否该拆分**：若新增内容与该存档原主题明显偏离（新内容占比过半且主题不同），改走功能 1 新建存档，并在两者 brief 的"相关存档"互加 see-also。
5. 同步 `INDEX.md` 中该存档所在行。
6. **报告**：说明合并了哪些要点、修改了什么。

## 功能 4：复用（reuse）

**触发**：新任务开始时（用户要求"复用经验/参考之前的做法"），或任务执行中遇到疑似有先例的问题。

1. 以当前任务 prompt 执行功能 2，取最相关 1–2 个存档。
2. 读其 `brief.txt`；仅当当前任务确实用得上时，再深入读 `experience.md` 及 path 引用的上下文文件。
3. **应用**：方案与执行中直接采用已验证的做法，规避已记录的坑；存档经验与当前任务实际情况冲突时，以当前任务为准。
4. 在回复中简要注明参考了哪些存档（文件夹路径）。
5. 本次任务成功后若产生新经验 → 回到功能 1/3 继续沉淀。

## 通用原则（所有功能遵守）

- **简要**：存档文字能短则短，细节靠 path 引用与 experience.md 分层承载。
- **path 引用优先**：上下文一律以绝对路径引用原文件（夹），不复制内容。仅当引用对象是易失文件（临时产物、会话结束即删）且很小且对复用必不可少时，才复制进该存档的 `assets/`。
- **独立性（去重）**：每个存档单独可读可懂，除"相关存档"的 see-also 弱引用外不得依赖其他存档；同一主题只保留一个存档，靠功能 3 增量演进。
- **安全**：不存密钥、密码、token 等敏感信息。
- **索引同步**：任何存档的增、改、并、删都必须同步 `INDEX.md`。
- **合并与删除**：发现两个存档高度重叠需合并时，先向用户确认；合并保留更通用的标题，被并入的文件夹在删除前再次向用户确认。
